## Two real findings, both new

1. **S2 delivery needs a same-/24 server.** With the Mac at 192.168.4.160 the unit fetched a URI
   once and then stalled; with aliases `192.168.5.160` / `192.168.6.160` (`ifconfig en0 alias`, no
   DNS change) every fetch landed immediately (`GET … 200`, and a `206` for a range probe). Prior
   sessions' "it only fetches sometimes" is very likely this.
2. **Playback from a local URL never leaves `STOPPED`** on 86.11 — before *and* after adding Range
   support, `application/dash+xml` vs `audio/aac` vs `audio/mpeg`, `res` duration/sample attributes,
   `Seek`, `Stop`+`Play`, volume 0. `GetTransportInfo` stays `STOPPED`, `RelTime 0:00:00`, while the
   fetch itself succeeds. If the transport never opens the stream to PLAYING, the audble parse may
   never arm — this is the prime suspect for the chain result below, not necessarily a code change.

## Transport lessons (both learned the hard way today)

- **A 0.25 s test track proves nothing**: playback ends instantly and the state reads `STOPPED`, so it
  looks broken. Generate a **20 s** track (`ffmpeg -f lavfi -i "sine=frequency=440:duration=20" …`) —
  with that, `.5.217` goes `PLAYING` and `RelTime` advances, i.e. the transport and the range server
  are both fine.
- **`Play` returns UPnP `701` when the media type is wrong for the build**, and the unit accepts the
  URI first, so a fire can look successful while nothing streams. On S1 (`57.23`) the working PI is
  `http-get:*:audio/aac:*` (`audio/audible` and `audio/mp4` both 701, and `aac` is not even in its
  Sink list). Always assert the **`Play` return code**, not just `SetAVTransportURI`.
- After a payload fire the `/status/VERSION` route can go **empty for minutes** while `/status/zp`
  still answers `200` — the daemon is degraded, not gone. `BootSeq` is the only trustworthy reboot
  detector.

## The current prime suspect: stage 1 no longer arms

After the S1 parser was cleared as a regression (below), the remaining link was measured directly.
On `.84`, the *stage-1* file (`A_toc_past_eof.aa`, 303 B) now answers **`Play` → 701** on every PI
tried (`audio/aac`, `audio/audible`), while the payload file itself answers **200** with `audio/aac`
in a fresh state. Order matters and the transport is fragile: payload-after-a-failed-stage1 → 200,
payload-after-a-playing-mp3 → 701.

The stage-1 bind is what sets `r22 != 0` for the payload parse (`RE_AUDIBLE.md`). If it never
binds, no payload can fire — which is consistent with every null result in this session on both
ISAs. Fixing the bind is the next thing to try, ahead of any further sweeping — but note the payload file
*also* 701s in most orders (only the first `SetAVTransportURI` after a real track answered 200), while
a real `.mp3` plays every time. That is a media-acceptance change, not a transport-state one: the
renderer no longer starts our `.aa` container at all in most orders. Next probes, in order:
**Resolved during this session:** the 701 was a *race*, not a media rejection. `Play` must be
**retried**: the renderer answers 701 until it has finished opening/probing the stream, then 200
(`ERR701, ERR701, ERR701, 200` observed, and a single attempt at 2 s/4 s/6 s failed before a 200 on
the third). So a fire is only armed when `Play` finally returns 200, and every probe now loops until
it does (≤10 tries). Earlier sweeps that used fixed 1.3 s settles and ignored the `Play` code were
blind and are void.

(a) a genuine Audible `.aa` (any DRM-free sample) — if it 701s too, the renderer dropped AA support;
(b) if only ours 701s, correct the container (real TOC sizes instead of a TOC past EOF) and re-test;
(c) only then re-arm both stages and re-sweep.

### Why every earlier sweep missed it (the oracle bug)

`calibrate` read `BootSeq` after the watch window; while a unit is *down* that read fails and yields
`-1`, so `b1 > b0` was false for exactly the cells that worked. Every "null" sweep in this session was
blind by construction. Fixed: a cell that is still down at the end of its window counts as a reboot,
the sweep waits for recovery, and only then re-reads `BootSeq`.

## Arg-control bypass: `mr r3, r29` gadgets (the junk dword is avoidable)

The 4-byte `&V` at `B` only corrupts the argument for functions that take `r3` directly. At the FN call
**`r29 = F`**, and `F` is set by our own observer cell — so a gadget that does `mr r3, r29; bl <fn>`
passes **node0, verbatim, no junk**. Found in the image (branch-target scan, 6 instruction reach):

| gadget | call | file op |
|---|---|---|
| `0x10008A3C` | `mr 3,29; bl 0x10546368` | **unlink** |
| `0x1000DEC8` / `0x1000DED4` / `0x1000E200` | `mr 3,29; …; bl open` | open |
| `0x1007D3C0`, `0x10095068`, `0x100A…` | `mr 3,30 / 28 / 26; …` | rename / unlink / open |

`build --isa ppc --at0` writes the string at node0 for exactly this class. First fire
(`FN=0x10008A3C`, path `/jffs/sys/debug/ssh/authorized_keys`) **rebooted** — inconclusive between
"unlink ran, the mid-function slice then crashed" and "gadget misbehaved"; the slice continues into
`lis 29,…` which clobbers the register the later code uses, so a *tail* gadget (one that ends in
`blr` right after the call) is the next thing to look for.

## The reboot is a property of the FIRE, not of the FN (measured)

Firing a payload whose FN is a bare `blr` stub — first in band, then at `0x10800000` (far outside any
heap band) — rebooted the unit both times (~95 s, `BootSeq` moves). So on 83121 **every armed `.aa`
fire reboots**, independent of S and of the FN. Consequences:

- `REBOOT` alone is not proof that the chain reached the FN; the band/S claim stands only on the
  earlier canary-era evidence and the `system()`-only differences.
- The observable must be **durable across the reboot** (a file), not a port or an outage.
- The automatic reboot is actually useful: plant, and the boot chain (`/etc/Configure`) executes.

Attempted exactly that: `sonosFileCreate(path, NULL, 0, 0)` at `0x1028ABF4` (`li 4,0; li 5,0; mr 3,29;
li 6,0; bl …`) with path `/jffs/system/Configure.dev` — the zero data/len removes the garbage-pointer
risk entirely. Fire rebooted, **port 23 stayed closed** afterwards, so either the create failed
(r29 ≠ node0, i.e. the gadget premise) or the file landed and telnetd still cannot bind — the two
hypotheses the next session must separate (e.g. plant `/jffs/hosts` and diff, or find an r29-witness).

### Correction: at the FN call `r29 = 0`, not `F` (disassembly)

The dispatcher body around the call is unambiguous:

```
102bf7b4: mr 3, 29          ; resolve(prev)  -- r3 = the object slot
102bf7b8: bl 0x102bdedc     ; -> B
102bf7bc: li 29, 0          ; *** r29 is ZEROED here ***
102bf7c4: mr 4, 28          ; r4..r7 = the notify ctx
102bf7c8: mr 5, 27
102bf7cc: mr 6, 26
102bf7d0: mr 7, 25
102bf7d4: mr 3, 9           ; r3 = B
102bf7e8: bctrl             ; FN(r3=B, r4..r7=ctx)
102bf7ec: mr 29, 3          ; r29 is only filled AFTER the call
```

So every `mr r3, r29` gadget passes **NULL**: `unlink(NULL)`/`sonosFileCreate(NULL,…)` fail silently, which is
exactly what the `/audio_tap` 403 shows. The only live argument is `r3 = B`, and B is the *junk-prefixed*
one — plus `r4..r7` = the notify ctx, which is not our memory. A full scan of `addi r3,r3,4`
tail-branches reaches only libc string/compare functions (strcmp, memcpy, memset, strlen, …), never a file
op; the single `lwz r3,4(r3); bl open` slice (`0x10298BEC`) was fired with a pointer at B+4 and also did
not create the file. Clean path control on S1 therefore needs either a *two-instruction* stub of our own
(no binder) or the emulator to place one.

### Where the wrapper's child dies (disassembly, then fires)

The child path is not subtle: after `fork` the child closes fds 3..255 and calls
**`execve(argv[0], argv, environ)` directly** (`lwz 3,0(29); lwz 5,<env>; mr 4,29; bl execve` at
`0x104046D4`) — no cap work, and `access(argv[0], X_OK)` is checked in the *parent* first, so an
unusable path cannot even fork. If `execve` fails the child formats the error and writes it to the pipe.

So the reboot means we got past `access` and reached `execve`. But **even a plain
`sh -c 'wget …/HELLO'` through the wrapper is silent** (no request ever reaches the server, and the
harness log file is not even created) — so the failure is *before or at the exec*, not telnetd's own
startup needs. `/bin/sh`, `/bin/busybox` and `/usr/sbin/telnetd` all exist on 83121 (rootfs checked),
so it is not a missing binary either. Fires: `/usr/sbin/telnetd` directly, via
`sh -c '… &'`, and via `busybox setsid` — **all exec, none binds**. `/dev/pts` is mounted at boot
(`rcS`) and the pty path is therefore not the excuse. The remaining reasons are telnetd's own startup
needs in this context (no `-i`/inetd mode, utmp, or the fork/daemonize step) — the next instrument is
the child's *own* stderr, which needs a reader we do not have yet (`/jffs` is not readable pre-auth).

### The S1 unlock oracle, and the plant verdict

`/audio_tap?tap=test` is a pre-auth unlock **oracle** on this build: **403** = flag absent, **404** =
gate passed (`FIRMWARE_PATHS`, measured again here). Checked right after the plant fire: **403**, so
`/jffs/system/Configure.dev` was **not** created — the `sonosFileCreate` slice did not do its job.
That makes the r29 premise the thing to disprove first: docs say `r29 = F`, but if it is not, every
`mr r3,r29` gadget passes an unrelated pointer. The oracle makes that cheap to settle — one fire per
candidate register family, then a single `403/404` read (no ports, no /jffs access needed).

## The wall is now one sentence: no child process runs at all

2. `system@plt` + `;mkdir -p /jffs/system;touch /jffs/system/Configure.dev` — reboot, and

the chain — arming, parse, dispatch, the FN call — demonstrably does.

## Emulator results (first real use, and they are useful)

Under `qemu-ppc` + `gdb-multiarch` on css, breaking at `open()` during startup:

- `system("/bin/touch /tmp/PROOF_GDBCALL")` → file created, `fork` observed, return 0. **Works.**
- the junk-prefixed form `system("\020lPh;/bin/touch /tmp/PROOF_JUNK")` → file created. **The `;`
  trick is sound.**
- `open("/tmp/PROOF_OPEN", 0x241, 0644)` (O_WRONLY|O_CREAT|O_TRUNC) → created. **API fine.**
- the mid-function slice `0x10298BEC` (`lwz r3,4(r3); …; bl open`) called with a fake B →
  **SIGSEGV in libpthread**: the slice is not frame-safe, which is why the device fire created
  nothing either.

So the next real step is a *heap-executable test*: if the 24 KB node page is executable, a
three-instruction stub (`li r4,0x241; addi r3,r3,4; b open@plt`) can live in the payload and is
verified cheaply in the emulator first. First device attempt (`STUB_OPEN`, `STUB_CONF`) rebooted with
no file, but that is indistinguishable from the stage-1 reboot above — the emulator must judge it.

## Converging conclusion: on 83121 the payload parse does not run at all

Everything points one way. A payload-less fire (stage-1 twice) is indistinguishable from any payload
fire: same ~90 s reboot, same silence. Four payload classes were fired with delivery confirmed — a
bytecode-free `blr`, `system` with a `touch`, the exec wrapper with a shell/beacon, and a
three-instruction **heap stub** (`li r4,0x241; addi r3,r3,4; b open@plt`) aimed at both
`/jffs/system/Configure.dev` and `/tmp/device_unlocked_flag` — and none produced a single side effect
(`/audio_tap` stays 403 throughout; the flag stub was polled every 1.5 s for 40 s while it fired).

If the FN were being called, the flag stub alone would have flipped `/audio_tap` to 404 within
seconds and before any reboot. It did not. So the chain on 83121 breaks **before the FN call** — the
payload is fetched and played, but not parsed into the strcpy/dispatch path — and the reboot we kept
reading as progress is the stage-1 bind's watchdog.

That is the next thing to prove or break: feed the emulated daemon a `SetAVTransportURI` with the
payload on its loopback (it does not bind :1400 yet — the MDP/model wall — which is the first thing to
fix there), or instrument the parse entry directly in gdb.

## Emulator rig, second pass: it runs, it just never finishes init

Set up on css this round: `mtdram` loaded (gives `/dev/mtd0`), `GCModel S16` appended to the staged
conf, `/ramdisk/optlog` created (the rootfs links `/opt/log` there), and helper scripts
`run_acg.sh` (with `-g 1234`), `run_ac2.sh`, `fg.sh`, `probe_trace.sh` staged at `/tmp` on css.

Results: the daemon **runs and stays up** under `qemu-ppc` (a 12 s foreground run ends on the timeout,
not on an exit; `fork`/`system`/`open` all work under gdb), but it binds **nothing** on 1400/1401/1410
and writes no `anacapa.trace` in this environment — the old trace file in `/ramdisk/optlog` is from the
October rig. It is the same init wall the S2 rig hit (model/MDP), and it has to be cleared before the
parse can be driven over loopback. A `break bind` probe did not even hit inside 90 s, so init stops *before* the first bind.

`strace -f` on the guest is the better instrument and is now the recorded path: it shows the last
syscalls before the stop. That produced two concrete facts and one new blocker — the daemon opens
`/dev/chk` then `/dev/audioctl` and **stops dead right after that open** (no further syscalls, only a
repeating `SEGV_ACCERR` storm at `0x40836B48` / `0x1054xxxx`). Creating the device nodes
(`mknod audioctl c 1 5`, `chk c 1 5`, plus `pts/`, `ptmx`, `console`, `nulld`, `led*`, `mtd1..3`) moved
the start-up LED error from `Error 1 opening LED device` to `Error 3 writing LED pattern`, i.e. the node
work is real progress. A 60 s run with the nodes as **fifos** behaves identically (stops right after `open(/dev/audioctl)`,
**zero** `bind()` calls in an strace that covers `file,ioctl,read`) and never binds in 60 s. So it is not
the node *type*; the daemon parks immediately after that open. An **unfiltered** strace shows why it never binds: right after that open the daemon enters a
`SIGSEGV`/`mprotect` **fault loop** at fixed addresses (`0x40836B48`, `0x105463E0`, `0xFC02CF4`, …) —
each write faults, qemu's handler flips the page writable, `rt_sigreturn`, flip back read-only, repeat. It
is the guest's own PLT/GOT self-modification being re-faulted, and `-one-insn-per-tb` does not change it.
That loop, not a missing node, is the emulator's current wall.

Next: emulate `audioctl` better (it is a Sonos DSP char device; a zero char
device already beats a regular file) or find the switch that skips audio init, then re-run the bisect.

## CORRECTION (2026-11-21): the icmp oracle was broken — most "no child runs / it reboots" claims are void

`icmp_ok()` matched the literal `" 0% packet loss"`, but macOS prints **`0.0%`**, so it returned False
for *every* target, live or dead. Consequences as published below and now fixed:

- `verdict` was `REBOOT` for every fire, and `icmp_losses` was simply the number of watch samples.
  So "the fire reboots", "stage-1 alone reboots", "`system()` always trips the watchdog" and
  "the wrapper reboots" were all **artefacts**.
- Re-measured with `parse_loss()` (regex, tested): **everything is clean and `BootSeq` never moves**.
  Stage-1 only → clean; `system(';true')` → clean; `system(';mkdir …;touch …/Configure.dev')` → clean;
  the reboot gadget `0x104123D8` → clean, `BootSeq` 122 before and after.

Re-measured with the fixed oracle and a fresh canary payload (`FN=0x51000000`, an unmapped address
that must crash): **`icmp_losses=1`, `verdict=clean`** — the FN is not reached. The same holds for the
**original device-proven artifact** `CAN135_00710000.aa` fired unchanged at its own address
(`icmp_losses=0`), so this is not our builder: the chain is inert on 83121. So on 83121 **nothing
fires at all** — not even the gadget that provably rebooted 74170 in October —
and the `/audio_tap` gate stays 403 after a plant attempt plus a fire. The parse-never-runs conclusion
survives, but for the right reason now: there is no observable effect of any kind, and no reboot to
misread. Everything below that mentions a reboot should be read as "was measured with the broken
oracle"; the ones re-measured are marked.

## A set while PLAYING is refused (so "play a real track first" cannot arm)

Two runs, with and without a preceding `Stop`: mp3 `SetAVTransportURI` 200 → `Play` 200 → then the
**payload's `SetAVTransportURI` answers 701**, `Play` 200, and nothing fires. So on 83121 a URI set is
rejected while the transport is really playing, and the two-stage protocol in fact depends on the
stage-1 `.aa` *not* playing (a TOC-past-EOF stream stays unplayable, so the second set is accepted).
That invalidates the "real track first" variant by construction, and reframes the gate: `r22` must be
set by the stage-1 **parse**, not by playback.

Also fixed: the harness server spammed a full `BrokenPipeError` traceback whenever a player aborts a
fetch (routine) — now swallowed.

## Two oracle regressions on 83121 (measured)

- **`POST /setstring` no longer kills the daemon.** Two accepted writes (`200`, value read back with
  `GetString`) left the unit pinging clean and `/status/zp` answering for minutes. The documented
  "one-request kill" is a 57.23-74170 property, so it can no longer be used as the crash control.
- **`/status` can outlive the daemon.** With the kill gone the status server is not a daemon-liveness
  signal, which makes every outage-poller suspect. Added `daemon_up()` / `calibrate --daemon-oracle`:
  anacapad's own watchdog socket **1410** (verified open on .84) is the liveness probe instead.
