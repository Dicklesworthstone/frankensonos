Goal: root on S2 hardware, using the Sonos-One SSH chain as the payoff.

## Two real findings, both new

1. **S2 delivery needs a same-/24 server.** With the Mac at 192.168.4.160 the unit fetched a URI
   once and then stalled; with aliases `192.168.5.160` / `192.168.6.160` (`ifconfig en0 alias`, no
   DNS change) every fetch landed immediately (`GET … 200`, and a `206` for a range probe). Prior
   sessions' "it only fetches sometimes" is very likely this.
2. **Playback from a local URL never leaves `STOPPED`** on 86.11 — before *and* after adding Range
   support, `application/dash+xml` vs `audio/aac` vs `audio/mpeg`, `res` duration/sample attributes,
   `Seek`, `Stop`+`Play`, volume 0. `GetTransportInfo` stays `STOPPED`, `RelTime 0:00:00`, while the
   fetch itself succeeds. If the transport never opens the stream to PLAYING, the audble parse may
   never arm — this is the prime suspect for the chain result below, not necessarily a code change.

## Transport lessons (both learned the hard way today)

- **A 0.25 s test track proves nothing**: playback ends instantly and the state reads `STOPPED`, so it
  looks broken. Generate a **20 s** track (`ffmpeg -f lavfi -i "sine=frequency=440:duration=20" …`) —
  with that, `.5.217` goes `PLAYING` and `RelTime` advances, i.e. the transport and the range server
  are both fine.
- **`Play` returns UPnP `701` when the media type is wrong for the build**, and the unit accepts the
  URI first, so a fire can look successful while nothing streams. On S1 (`57.23`) the working PI is
  `http-get:*:audio/aac:*` (`audio/audible` and `audio/mp4` both 701, and `aac` is not even in its
  Sink list). Always assert the **`Play` return code**, not just `SetAVTransportURI`.
- After a payload fire the `/status/VERSION` route can go **empty for minutes** while `/status/zp`
  still answers `200` — the daemon is degraded, not gone. `BootSeq` is the only trustworthy reboot
  detector.

## The current prime suspect: stage 1 no longer arms

After the S1 parser was cleared as a regression (below), the remaining link was measured directly.
On `.84`, the *stage-1* file (`A_toc_past_eof.aa`, 303 B) now answers **`Play` → 701** on every PI
tried (`audio/aac`, `audio/audible`), while the payload file itself answers **200** with `audio/aac`
in a fresh state. Order matters and the transport is fragile: payload-after-a-failed-stage1 → 200,
payload-after-a-playing-mp3 → 701.

The stage-1 bind is what sets `r22 != 0` for the payload parse (`RE_AUDIBLE.md`). If it never
binds, no payload can fire — which is consistent with every null result in this session on both
ISAs. Fixing the bind is the next thing to try, ahead of any further sweeping — but note the payload file
*also* 701s in most orders (only the first `SetAVTransportURI` after a real track answered 200), while
a real `.mp3` plays every time. That is a media-acceptance change, not a transport-state one: the
renderer no longer starts our `.aa` container at all in most orders. Next probes, in order:
**Resolved during this session:** the 701 was a *race*, not a media rejection. `Play` must be
**retried**: the renderer answers 701 until it has finished opening/probing the stream, then 200
(`ERR701, ERR701, ERR701, 200` observed, and a single attempt at 2 s/4 s/6 s failed before a 200 on
the third). So a fire is only armed when `Play` finally returns 200, and every probe now loops until
it does (≤10 tries). Earlier sweeps that used fixed 1.3 s settles and ignored the `Play` code were
blind and are void.

(a) a genuine Audible `.aa` (any DRM-free sample) — if it 701s too, the renderer dropped AA support;
(b) if only ours 701s, correct the container (real TOC sizes instead of a TOC past EOF) and re-test;
(c) only then re-arm both stages and re-sweep.

## S1 parser is NOT a regression (measured)

`57.23-83121`'s `anacapad` keeps the 74170 audible parser verbatim: all **33** `addi r3, X, 0x18EC`
(`session+6380`) sites are present in both, each shifted by exactly **+4** bytes (one small insertion
earlier in the image; binaries differ elsewhere but the parse region does not). So the chain layout
and the strcpy destination are unchanged on the current S1 build. Full band sweep
`0x106c0000-0x106d4000` (40 fires, every payload fetched) produced **no canary hit** — pointing at
arming rather than at offsets.

## BREAKTHROUGH: the chain DOES fire on 83121 — the band is 0x106c4e10

Two facts from the last fires:

- `fire TEL_HARNESS.aa 0x106c4e10` (FN = `system@plt`, `;telnetd…`): 83 s ICMP outage,
  `verdict=REBOOT`, and `BootSeq` went 97 → 122.
- `fire RBG.aa 0x106c4e10` (the reboot gadget alone): 95 s outage, `verdict=REBOOT`. **Confirmed.**
- `fire TEL_TRUE.aa` (`;true` through `system`): 66 s outage → **`system()` alone always trips the
  watchdog**, command or not. `&` and `setsid` do not help (the block is in `system()`).
- The **exec wrapper** (`FN=0x104044C0`, argv we place — new `build --isa ppc --wrap`) also reboots
  and still binds nothing, so the wrapper forks fine but the child dies.

### Why every earlier sweep missed it (the oracle bug)

`calibrate` read `BootSeq` after the watch window; while a unit is *down* that read fails and yields
`-1`, so `b1 > b0` was false for exactly the cells that worked. Every "null" sweep in this session was
blind by construction. Fixed: a cell that is still down at the end of its window counts as a reboot,
the sweep waits for recovery, and only then re-reads `BootSeq`.

## Arg-control bypass: `mr r3, r29` gadgets (the junk dword is avoidable)

The 4-byte `&V` at `B` only corrupts the argument for functions that take `r3` directly. At the FN call
**`r29 = F`**, and `F` is set by our own observer cell — so a gadget that does `mr r3, r29; bl <fn>`
passes **node0, verbatim, no junk**. Found in the image (branch-target scan, 6 instruction reach):

| gadget | call | file op |
|---|---|---|
| `0x10008A3C` | `mr 3,29; bl 0x10546368` | **unlink** |
| `0x1000DEC8` / `0x1000DED4` / `0x1000E200` | `mr 3,29; …; bl open` | open |
| `0x1007D3C0`, `0x10095068`, `0x100A…` | `mr 3,30 / 28 / 26; …` | rename / unlink / open |

`build --isa ppc --at0` writes the string at node0 for exactly this class. First fire
(`FN=0x10008A3C`, path `/jffs/sys/debug/ssh/authorized_keys`) **rebooted** — inconclusive between
"unlink ran, the mid-function slice then crashed" and "gadget misbehaved"; the slice continues into
`lis 29,…` which clobbers the register the later code uses, so a *tail* gadget (one that ends in
`blr` right after the call) is the next thing to look for.

## The reboot is a property of the FIRE, not of the FN (measured)

Firing a payload whose FN is a bare `blr` stub — first in band, then at `0x10800000` (far outside any
heap band) — rebooted the unit both times (~95 s, `BootSeq` moves). So on 83121 **every armed `.aa`
fire reboots**, independent of S and of the FN. Consequences:

- `REBOOT` alone is not proof that the chain reached the FN; the band/S claim stands only on the
  earlier canary-era evidence and the `system()`-only differences.
- The observable must be **durable across the reboot** (a file), not a port or an outage.
- The automatic reboot is actually useful: plant, and the boot chain (`/etc/Configure`) executes.

Attempted exactly that: `sonosFileCreate(path, NULL, 0, 0)` at `0x1028ABF4` (`li 4,0; li 5,0; mr 3,29;
li 6,0; bl …`) with path `/jffs/system/Configure.dev` — the zero data/len removes the garbage-pointer
risk entirely. Fire rebooted, **port 23 stayed closed** afterwards, so either the create failed
(r29 ≠ node0, i.e. the gadget premise) or the file landed and telnetd still cannot bind — the two
hypotheses the next session must separate (e.g. plant `/jffs/hosts` and diff, or find an r29-witness).

### Correction: at the FN call `r29 = 0`, not `F` (disassembly)

The dispatcher body around the call is unambiguous:

```
102bf7b4: mr 3, 29          ; resolve(prev)  -- r3 = the object slot
102bf7b8: bl 0x102bdedc     ; -> B
102bf7bc: li 29, 0          ; *** r29 is ZEROED here ***
102bf7c4: mr 4, 28          ; r4..r7 = the notify ctx
102bf7c8: mr 5, 27
102bf7cc: mr 6, 26
102bf7d0: mr 7, 25
102bf7d4: mr 3, 9           ; r3 = B
102bf7e8: bctrl             ; FN(r3=B, r4..r7=ctx)
102bf7ec: mr 29, 3          ; r29 is only filled AFTER the call
```

So every `mr r3, r29` gadget passes **NULL**: `unlink(NULL)`/`sonosFileCreate(NULL,…)` fail silently, which is
exactly what the `/audio_tap` 403 shows. The only live argument is `r3 = B`, and B is the *junk-prefixed*
one — plus `r4..r7` = the notify ctx, which is not our memory. A full scan of `addi r3,r3,4`
tail-branches reaches only libc string/compare functions (strcmp, memcpy, memset, strlen, …), never a file
op; the single `lwz r3,4(r3); bl open` slice (`0x10298BEC`) was fired with a pointer at B+4 and also did
not create the file. Clean path control on S1 therefore needs either a *two-instruction* stub of our own
(no binder) or the emulator to place one.

### The S1 unlock oracle, and the plant verdict

`/audio_tap?tap=test` is a pre-auth unlock **oracle** on this build: **403** = flag absent, **404** =
gate passed (`FIRMWARE_PATHS`, measured again here). Checked right after the plant fire: **403**, so
`/jffs/system/Configure.dev` was **not** created — the `sonosFileCreate` slice did not do its job.
That makes the r29 premise the thing to disprove first: docs say `r29 = F`, but if it is not, every
`mr r3,r29` gadget passes an unrelated pointer. The oracle makes that cheap to settle — one fire per
candidate register family, then a single `403/404` read (no ports, no /jffs access needed).

So delivery and arming are no longer the gap: the payload is fetched, the stream starts, and the
daemon shows a post-fire state change — but no FN is reached. What is left is the parse itself on
83121: the type-2 record → `strcpy(session+6380)` → observer cell → notify → FN. The parser text is
byte-identical, so the suspicion is now the **session/observer offsets** (the 30000 witness, the
notify ctx) rather than the parser or the container. A first diff pass (below) says the structure is intact, so the suspicion moves to the **gate state**
(`r22`), not the code.

## 83121 offset map (diff pass, done)

Everything the chain needs survives, shifted by a constant:

| item | 74170 | 83121 |
|---|---|---|
| `strcpy(session+6380)` dst site | `0x10115478` | `0x1011547C` (+4) |
| guard `cmpwi cr4,r22,0 / beq` + `addi r30,r31,0x18EC` | `0x1011546C` | `0x10115470` — **byte-identical** (`419201e0 3bdf18ec`) |
| dispatcher prologue (`mflr; stwu; addi r9,r3,0x17d4; …`) | `0x102bf778` | `0x102bf784` (+0xC; the function is unchanged — `mtlr r0; blr` now precedes it) |
| `session+30000` witness sites | 61 | 60, all +4 |
| S2 equivalent: `0x18EC` constant occurrences | 86.10: 14 | 86.11: 13 (offset kept, one site fewer) |

So the parser, the guard, the destination, the witness offset and the dispatcher are all present and
unchanged; only addresses moved. What is *not* answered is whether `r22 != 0` is ever established —
i.e. whether the stage-1 bind still sets the gate on this build. That, plus a reliable
crash detector (the daemon restart is very fast: a 0.2 s `/status` poll is not proof either way), is
the next unit of work.

## Two oracle regressions on 83121 (measured)

- **`POST /setstring` no longer kills the daemon.** Two accepted writes (`200`, value read back with
  `GetString`) left the unit pinging clean and `/status/zp` answering for minutes. The documented
  "one-request kill" is a 57.23-74170 property, so it can no longer be used as the crash control.
- **`/status` can outlive the daemon.** With the kill gone the status server is not a daemon-liveness
  signal, which makes every outage-poller suspect. Added `daemon_up()` / `calibrate --daemon-oracle`:
  anacapad's own watchdog socket **1410** (verified open on .84) is the liveness probe instead.
