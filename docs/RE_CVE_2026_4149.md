## The advisory (verbatim facts)

SSA-2026-0001 (2026-03-25, CVE-2026-4149, High): "A vulnerability exists in the
SMB protocol client implementation within Sonos S2 systems which allows an
attacker to force a protocol downgrade to a vulnerable version. This
vulnerability does not affect Sonos S1 systems. Known Attack Vectors: A
malicious actor on the same local network could send a specially crafted SMB
response to the device potentially leading to arbitrary code execution."
Affected: "All releases prior to Sonos Systems release v17.7 (build
92.0-72171)". Reported via Pwn2Own 2025.

Our S2: 86.10-81100 < 92.0-72171 → inside the affected range. S1 57.23: not
affected per the advisory (and its SMB client closes the connection before
NEGOTIATE — `RE_GETAA_DATALENGTH.md`, so the surface differs too).

## Wire reachability (already measured, RE_GETAA_DATALENGTH)

`GET /getaa?u=x-file-cifs://<us>:<port>/S/folder.jpg` makes an S2 player
(86.10) connect to our server and run NEGOTIATE → SESSION_SETUP ×2 (NTLMSSP) →
TREE_CONNECT → CREATE → QUERY_INFO → READ — **unauthenticated, no device
configuration**. The client is libsmb2 4.0.0 (`libsmb2.so.4.0.0`, sha256
`ba823cc9…`). This is the delivery vehicle a downgrade answer rides on.

## Static map of the downgrade logic (libsmb2 v4.0.0 source, tag 2ef9bb7)

Every claim below is an upstream source line at that tag; the shipped binary is
the same source line family as the three proven decoders (§7c RE_CVES).

1. **The client offers every dialect pre-auth.** `smb2_init_context()`
   (lib/init.c:292) defaults `smb2->version = SMB2_VERSION_ANY`, and
   `smb2_connect_async()` (lib/libsmb2.c:950-958) then sends
   `dialect_count = 5` with `0x0202, 0x0210, 0x0300, 0x0302, 0x0311` — **SMB
   2.0.2 is in the offer**, unless the caller pinned `vers=` (a URL-argument
   only path; see 4).

2. **The reply dialect is accepted without any membership check.**
   `smb2_process_negotiate_fixed()` (lib/smb2-cmd-negotiate.c:243) reads
   `dialect_revision` (u16 at reply offset 4) and never compares it against the
   offered list — any u16 the server answers with is adopted
   (`smb2->dialect = rep->dialect_revision`, lib/libsmb2.c:860).

3. **The downgrade protections that exist are conditional on the caller.**
   Signing is enforced only when `smb2->sign` was set (default 0; lib/init.c
   sets it only from a `sign` URL arg): an unauthenticated server answering
   `security_mode = 0` is accepted (lib/libsmb2.c:884-889). Encryption is
   checked only when `smb2->seal` was requested. For an answered dialect
   **< 3.1.1** the pre-auth-hash binding is simply absent: the 3.1.1 signing
   key derivation mixes `smb2->preauthhash`, and the preauth hash is only
   updated when the negotiate carries the 3.1.1 contexts — a 2.0.2/2.1/3.0
   answer therefore has **no integrity binding between negotiate and
   session**, which is the structural property the advisory's "force a
   protocol downgrade" needs.

4. **Whether the S2 art caller pins vers/sign is the one unknown.** The caller
   lives in the encrypted base rootfs (the art handler that allocates the
   0x4000 buffer, RE_GETAA_DATALENGTH §Limits). The `smb2_init_context()`
   defaults make the downgrade path open **unless** that caller calls
   `smb2_set_version()/`vers=` or `smb2_set_sign()`. The device run answers
   this from the wire: if the client accepts a 2.1-only answer and proceeds to
   SESSION_SETUP, the caller did not pin anything.

5. **3.1.1-answer parsing has its own weak spot** (secondary, same surface):
   `smb2_parse_negotiate_contexts()` (lib/smb2-cmd-negotiate.c:204) ignores the
   return value of `smb2_get_uint16/uint32` (which do bounds-check and leave
   the target unchanged on failure) and advances `offset` before validating
   `offset > iov->len` — a 3.1.1 answer with a context whose `offset+len`
   exceeds the iov makes later iterations parse stale `type`/`len` words. The
   offsets stay inside the iov buffer only by the prior iteration's luck. A
   bounded OOB-read candidate, not a write; listed for completeness.

6. **What the downgrade buys.** At 2.0.2/2.1 the session key IS the signing key
   (lib/libsmb2.c:693-697) and there is no encryption-capability check; the
   2023/2025-era libsmb2 fixes the advisory ships were in the same
   reply-decoder family as CVE-2026-110712/13/14 (§7c/§9a RE_CVES — all three
   already ASan-proven on this exact tag). The advisory's RCE claims a fault
   in the downgraded-version parser path; on our tag the named unbounded
   decoders are the three over-reads, so the working hypothesis for the device
   run is: downgrade accepted → reply decoders parsed with weaker/absent
   validation → drive the proven over-read shapes through the downgraded path.

## Harness (offline, committed)

`recon/smb4149/negprobe.py` — a from-scratch SMB server that logs the client's
NEGOTIATE dialect list verbatim and answers with a chosen dialect
(`--dialect 0x0210` pins 2.1; default answers the client's best). It answers
NEGOTIATE and stubs SESSION_SETUP so the observation reaches "did the client
accept the downgrade and continue". No device contact until approved.
