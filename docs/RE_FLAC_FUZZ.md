# RE_FLAC_FUZZ — libFLAC 1.3.4 decode-path diff + targeted triggers (bead frankensonos-81v)

Lane: libFLAC **1.3.4** (`reference libFLAC 1.3.4 20220220` string confirmed in the 57.23
`opt/bin/anacapad`, statically linked, 34 `FLAC__` strings incl. `SEEK/TELL/LENGTH` status enums →
the seek callbacks are registered, so the seeking path is live on device). Delivery is the proven
hls_det vehicle (unauthenticated `SetAVTransportURI` + `Play`, decode in-process in anacapad = pre-auth
reachable). This lane: diff 1.3.4 against the 1.4.x/1.5.0 decode-path fixes, build 1.3.4 exactly
(NDEBUG, no-ogg, no-asm) under ASan+UBSan, craft targeted triggers for every unfixed path, and sweep.

## Rig

- Upstream: `github.com/xiph/flac`, tag `1.3.4` checked out at `/tmp/flac-134` (gitignored location;
  harnesses in `recon/flacfuzz/`, triggers generated by `recon/flacfuzz/mktriggers.py`).

  hello-world stalls); Apple clang's runtime is fine. All results below are Apple-clang builds.

The 89 assert-build aborts are a single signature:
`assert((br->consumed_bits & 7) == 0) in FLAC__bitreader_reset_read_crc16` (bitreader.c:337).
The device lib is a release build → `FLAC__ASSERT` compiles out. The violated invariant would mis-align
the CRC16 accumulation → spurious CRC mismatches (wrong-audio/sync churn), not memory unsafety.

## Verdict for the bead

**Falsifier branch tested and the honest result is negative on memory safety:** 1 300 deterministic
sanitizer cases + 9 targeted triggers over the exact 1.3.4 decode path produce **zero** ASan/UBSan
reports and zero hangs. Every memory-safety-relevant commit in the 1.3.4→1.5.0 range is either
(a) unreachable on device (LE-only bitreader swap on a BE target; 33-bps rejected earlier;
147cfc8d's UAF needs machinery 1.3.4 doesn't have), (b) robustness/wrong-audio (residual bound,
datapath selection, blocksize 65536), or (c) not attacker-shaped (OOM state).

The two device-facing residues, both DoS/CPU-class, consistent with CODEC_EXPOSURE.md:

1. **`95064f9f` gap-fill amplification is live in 1.3.4** (fixed only in 1.4.0): a stream of tiny
   frames with `blocksize < 16` after a corrupt header makes the decoder emit up to
   `5 × sample_rate` silence callbacks per gap at `blocksize` samples each — for 44.1 kHz that is
   up to ~220 k write callbacks per gap, each handled in-process by anacapad. A CPU-amplification
   lever that stacks with the existing `/notify` stall economics; not a crash.
2. **`499f85f9` NULL vorbiscomment entries**: the 1.3.4 *library* hands `entry=NULL` to the client for
   zero-length comments. Whether anacapad's metadata consumer dereferences without a NULL check is a
   **binary-side question** (one `strncpy`/`strlen` on the entry pointer in the decoder wrapper) — the
   only candidate memory-safety follow-up this lane leaves open.

Device-verdict path (needs coordination per lane rules): serve `t6_vcnull.flac` and a
`blocksize<16` gap-fill stream through the hls_det vehicle on the bench unit; verdict = SWGen
unchanged + transport behavior, compared against the harness predictions above.
